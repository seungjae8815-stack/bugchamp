# SQL 마이그레이션 절차

`docs/` 에 `_sql_*.sql` 이 날짜 접두어로 쌓여 있지만 **적용 여부를 아무도 기록하지 않았다.**
이 스킬은 그 구멍을 메운다. 대장은 `docs/sql_migrations.md` 다.

## 1. 파일 이름 규칙

```
docs/_sql_YYYYMMDD_<짧은_영문_이름>.sql
```

같은 날 둘 이상이면 이름으로 구분한다(`_a`/`_b` 같은 접미어 금지 — 무엇을 하는지가 이름에 있어야 한다).

## 2. 파일 안에 반드시 들어갈 것

```sql
-- 목적: (한 줄. 왜 필요한가)
-- 작성: YYYY-MM-DD
-- 위험: (없음 / 데이터 손실 가능 / 잠금 발생 등)
-- 되돌리기: (아래 ROLLBACK 절 또는 "되돌릴 수 없음 — 이유")

begin;

-- 여기에 변경

commit;

-- ROLLBACK (적용 후 문제가 생기면 이걸 돌린다)
-- begin;
--   ...
-- commit;
```

`begin`/`commit` 로 감싸지 않은 마이그레이션은 만들지 않는다. 중간에 실패하면 스키마가
반쯤 바뀐 채 남고, 그 상태를 알아채는 건 앱이 깨진 뒤다.

## 3. 안전 규칙

- **컬럼을 삭제하거나 이름을 바꾸지 않는다.** 구버전 앱이 아직 그 컬럼을 읽는다.
  새 컬럼을 더하고, 구버전이 다 빠진 뒤 다음 마이그레이션에서 지운다.
- `not null` 컬럼을 추가할 땐 **반드시 `default` 를 함께** 준다. 없으면 기존 행에서 실패한다.
- 큰 테이블 인덱스는 `create index concurrently` 를 쓴다(트랜잭션 밖이어야 하므로 이때만
  `begin/commit` 을 나눈다. 파일 머리말에 그 이유를 적는다).
- RLS 를 켜는 변경은 **정책을 먼저 만들고** 켠다. 순서를 바꾸면 그 순간부터 아무도 못 읽는다.
- 일회성 데이터 보정은 `update` 전에 같은 `where` 로 `select count(*)` 를 먼저 돌려
  **몇 행이 바뀌는지 사용자에게 보여주고 확인받는다**.

## 4. 적용

사용자가 Supabase SQL Editor 에서 직접 돌린다. 너는 돌리지 않는다.
돌릴 SQL 을 그대로 붙여넣을 수 있게 코드 블록으로 제시하고, 예상 영향 행 수를 함께 말한다.

## 5. 대장에 기록한다

`docs/sql_migrations.md` 표에 한 줄 추가한다. 적용 전에는 `대기`, 사용자가 돌렸다고 하면 `적용`.
이 줄을 빼먹으면 이 스킬을 만든 이유가 없어진다.

## 6. 앱·서버 쪽도 함께 본다

스키마가 바뀌면 `packages/server` 의 쿼리와 `supabase/functions/` 의 Edge Function 도 같이 봐야 한다.
서버만 고치고 Edge Function 을 두면 일일 리포트가 조용히 깨진다.
