# 수익화 기획 (IAP + 광고)

> 확정: 2026-07-20. 수치는 전부 `packages/app/assets/data/iap.json` (§6 — 코드 하드코딩 금지).
> 원칙: **스탯 직접 판매 금지**(§2.6). 판매 범위는 *편의 + 진행속도*까지 (사장님 확정).

## 1. 판매 경계 (P2W 정책)

| 판매 가능 | 판매 금지 |
|---|---|
| 광고 제거, 시간 단축(즉시완료), 슬롯 확장 | **곤충 스탯/포텐셜 직접 판매** |
| 젤리(프리미엄 화폐), 골드·재료 묶음 | 전투 승률을 직접 사는 아이템 |
| 코스메틱(스킨·테마) — 스탯 영향 0 | 상대보다 강해지는 전용 곤충 |
| 진행속도(오프라인 상한, 방치 획득량) | |

> 진행속도 상품은 무과금 격차의 근원이므로 **수치를 JSON으로 상시 조절**한다.

## 2. 상품 카탈로그

### ① 광고 제거 패스 `remove_ads` — ₩7,700 (비소모성)
- 강제 광고 제거.
- **보상형 광고도 전부 스킵하고 보상을 즉시 지급**(2026-08-06 사장님 결정).
  "광고 제거"를 샀는데 보상형은 계속 봐야 하면 산 의미가 없다.
  구현은 `ui/ad_gate.dart` 한 곳 — 광고가 걸린 보상은 전부 이 함수를 거친다.
- ⚠️ 단, **PvP 결투 티켓 광고의 하루 상한(30회)은 모두에게 동일**하다.
  광고제거 구매자는 *시간만* 아끼고, 결제로 결투 판수를 더 사지는 못한다
  (그러지 않으면 트로피 랭킹이 다시 무너진다 — `docs/PROJECT_STATUS.md` 결투 티켓).
- 매일 접속 시 젤리 10 자동 지급.

**적용 방식(2026-07-20 구현)**: 새 아트 없이 **ColorFilter** 로 처리한다.

`arena_theme`→ 전투 배경 색보정. 보유하면 **내 곤충 전 화면에 자동 적용**
(장착 UI 없음). **상대 곤충에는 적용하지 않는다** — 내 스킨이지 상대 것이 아니므로.
새 아트가 생기면 같은 자리에서 필터 대신 이미지로 갈아끼우면 된다.

- **지급 규칙 한 곳**: core_save `applyIapGrant` — 서버 `GameActions.grantPurchase` 와 앱 로컬 지급
  `SaveController.applyPurchase` 가 같은 함수를 부른다(기존 상품도 이 함수로 옮겼다).
- **산 알은 자동 분해하지 않는다**(`autoRelease: false`). 요정함이 차면 넘친 알은 기존 규칙대로 가루(높은 등급부터 넣는다).
- **계정당 1회**: 서버 소유 `SaveGame.boughtOnce`. 두 번째 영수증은 스타터와 같이 `already_owned`(운영 지급 뒤 진짜 결제만 멱등 성공).
- **주 1회**: 서버 소유 `SaveGame.weeklyBought`(상품 id → 주 id). 막는 곳은 **앱 상점뿐**(버튼 비활성 + "다음 주 월요일 09시").

- **성장 패스 매일 몫**: 기기가 준다(곤충학자 패스 매일 젤리와 같다, `claimGrowthPassDaily`, 기기 날짜 키 `_growthDaily`).
  앱 실행·서버 세이브 채택(=결제 직후) 때 받는다. 밀린 날은 몰아주지 않는다. 하루 몫이 서버 업로드 검사 여유
  (가루 500 · 속성석+가속기 10 · 스킬 조각 급증 여유)보다 한참 작아야 한다 — `server/test/iap_products_test.dart` 가 본다.
  만료 시각 `growthPassExpiresAt` 은 서버 소유.
- 운영 지급(`/admin/grant`)으로 이 상품을 주면 요정·조각은 **기기 권위 필드**라 다음 업로드에 덮일 수 있다 —
  응답의 `deviceGoodsNeedsCheck` 가 참이면 확인하고, 덮였으면 `/admin/mail` 의 요정 칸으로 다시 보낸다.

## 3. 기술 설계

- **패키지**: `in_app_purchase`(Flutter 공식). 소모성(젤리) / 비소모성(광고제거·스킨) / 기간제(패스).
- **데이터**: `assets/data/iap.json` → `IapConfig`(core_run, 순수 Dart).
- **세이브 v16**: `adsRemoved`, `starterBought`, `ownedSkins[]`, `passExpiresAt`.
- **복원(restore)**: 비소모성 필수(스토어 심사 항목).
- **영수증 검증**: 초기 로컬 → 이후 Supabase Edge Function 서버 검증.
- **화면**: 상점 탭 `[제작 | 상점]` 2섹션.

## 6. 영수증 서버 검증 — ✅ 구현(2026-07-20)

| 항목 | 상태 |
|---|---|
| 같은 구매 중복 지급 차단 | ✅ 세이브 `redeemedPurchases`(기기별) |
| 지급 실패 시 완료 통보 보류(재전달 유도) | ✅ |
| **영수증이 진짜 구글 발급인지 검증** | ✅ Edge Function `verify-purchase` |
| **한 영수증을 여러 계정이 재사용** | ✅ `verified_purchases` 기본키로 차단 |

설정 절차는 `docs/backend_supabase.md` §9.
**서비스 계정 생성·Play Console 권한 부여·함수 배포는 사장님 작업**이다.

### 판정별 동작
- 진짜 → 지급 + 완료 통보
- 위조/취소/재사용 → 지급 안 함 + 완료 통보(재시도 무의미)
- **판정 불가(네트워크·점검) → 지급도 완료통보도 안 함 → 다음에 재시도**
  정상 구매자가 오프라인이라는 이유로 손해 보지 않게 하는 쪽을 택했다.

### ⚠️ 이걸로도 못 막는 것
진행도가 기기(Hive)에 있고 클라이언트가 자기 세이브를 쓰므로,
**앱을 개조해 결제 흐름을 건너뛰는 것**은 여전히 가능하다.
검증이 막는 것은 결제 후킹 앱의 **위조 영수증**(현실의 주된 위협)과
영수증 재사용이다. 완전 차단은 재화를 서버 권위로 옮겨야 하는데,
게임 구조를 통째로 바꾸는 일이라 지금 단계에선 과하다.
