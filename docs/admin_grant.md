# 특정 계정에 IAP 상품 지급 (`/admin/grant`)

보상·사과·테스트 목적으로 **결제 없이** 상품을 넣어 준다.

## 왜 이렇게 만들었나

지급 로직을 따로 쓰지 않고 **결제 경로(`grantPurchase`)를 그대로 재사용**한다.
따로 쓰면 "산 사람과 받은 사람의 상태가 다른" 버그가 조용히 생긴다 — 패스
연장 규칙, 스타터 1회 제한, 스킨 소유가 전부 결제와 똑같이 처리된다.

세이브는 **서버 저장본을 직접 고친다**. 패스·스타터는 서버 소유 필드
(`GameActions._serverOwnedKeys`)라 앱이 올려도 서버 값으로 덮이므로, 서버에
넣어야 실제로 들어간다.

## 쓰는 법 — 운영 패널 (권장)

`https://bugchamp-server-.../admin` → **지급** 탭.

1. 유저 uuid 붙여넣기
2. 상품 고르기 (목록은 서버의 `iap.json` 에서 실시간으로 받아온다 —
   화면에 박아 두면 상품이 바뀔 때 조용히 낡는다)
3. **사유** 입력 (중복 지급을 막는 열쇠 — 아래 참고)
4. 지급하기

지급 후 화면에 **패스 만료일·스타터 보유 여부**가 그대로 찍힌다. "이미
지급된 건입니다"와 "지급 완료"를 구분해서 보여준다 — 뭉쳐 놓으면 두 번
눌러 놓고 두 배로 들어간 줄 안다.

## 쓰는 법 — 명령줄

```powershell
$key  = "<ADMIN_KEY>"    # Secret Manager 의 bugchamp-admin-key
$url  = "https://bugchamp-server-867649520275.asia-northeast3.run.app/admin/grant"
$uid  = "<유저 uuid>"     # 아래 '유저 찾기' 참고

# 스타터 패키지
irm $url -Method Post -Headers @{ "x-admin-key" = $key } `
  -ContentType "application/json" `
  -Body (@{ userId=$uid; productId="starter_pack"; reason="2026-09-보상" } | ConvertTo-Json)

# 곤충학자 패스 (30일)
irm $url -Method Post -Headers @{ "x-admin-key" = $key } `
  -ContentType "application/json" `
  -Body (@{ userId=$uid; productId="idle_pass"; reason="2026-09-보상" } | ConvertTo-Json)

# 무한 버프 패스 (30일)
irm $url -Method Post -Headers @{ "x-admin-key" = $key } `
  -ContentType "application/json" `
  -Body (@{ userId=$uid; productId="buff_pass"; reason="2026-09-보상" } | ConvertTo-Json)
```

응답에 `passExpiresAt` · `buffPassExpiresAt` · `starterBought` 가 실려 온다 —
**들어갔는지 눈으로 확인할 것**.

## ⚠️ `reason` 이 중복 지급을 막는다

`purchaseId` 를 `admin:<상품>:<사유>` 로 만든다. 같은 사유로 두 번 부르면
두 번째는 **조용히 무시**되고 `alreadyGranted: true` 가 온다(멱등).

- 실수로 두 번 눌러도 두 배로 나가지 않는다.
- **일부러 더 주려면 사유를 바꾼다** — `reason="2026-09-보상2"`.
- 나중에 세이브만 봐도 `admin:` 접두사로 **결제가 아니라 지급**임을 구분한다.

## 유저 찾기 (uuid)

Supabase SQL Editor:

```sql
select id, nickname, trophies, stage, tier
from profiles where nickname = '<닉네임>';
```

닉네임은 바뀔 수 있으니 **uuid 를 기록해 둔다**. 문의(텔레그램)로 들어온 건은
메시지 하단에 uid 가 함께 찍힌다 — 그걸 쓰면 정확하다.

## 상품 id

| id | 종류 | 내용 |
|---|---|---|
| `starter_pack` | starter | 스타터 패키지(계정당 1회) |
| `idle_pass` | pass | 곤충학자 패스 30일 |
| `buff_pass` | buffPass | 무한 버프 패스 30일 |
| `jelly_s` … `jelly_xxl` | jelly | 젤리 팩 |
| `skin_gold_rhino` · `skin_albino_stag` | skin | 스킨 |

id 를 틀리면 404 와 함께 **아는 id 목록**을 돌려준다.

## 적용 시점

서버 저장본을 바꾸므로, 유저 앱은 다음 동기화(최대 60초) 또는 재접속에
반영된다. 앱이 켜져 있으면 로컬이 더 진행된 것으로 판단해 잠깐 미뤄질 수
있다 — 그때도 다음 업로드/재접속에 서버 값이 이긴다(패스는 서버 소유 필드).

## ⚠️ 소모품은 **우편으로 간다**(세이브에 쓰면 사라진다)

골드·젤리·재료는 **서버 소유 필드가 아니다** — 유저가 스스로 버는 값이라
서버가 소유할 수 없다. 세이브에 직접 써 놓으면 앱이 다음에 올리는 세이브의
값으로 **덮인다**. 2026-09-01 실기에서 "젤리 팩(4,200)을 줬는데 안 들어왔다"가
정확히 이것이었다.

그래서 `/admin/grant` 는 상품을 두 갈래로 나눠 보낸다:

| 부분 | 어떻게 | 유저가 할 일 |
|---|---|---|
| 패스·스타터·스킨·광고제거 | 세이브에 직접(서버 소유 필드) | 없음 — 바로 적용 |
| 골드·젤리·재료 | **우편** | 우편함에서 **받기** |

응답의 `mailed` 가 false 인데 `consumable` 이 true 면 우편이 실패한 것이다 —
우편 탭에서 손으로 보내야 한다.

⚠️ **부화기 슬롯**(스타터 패키지의 +1)은 우편으로도 못 보낸다. 젤리로도 사는
값이라 서버가 소유하지 않는다(§2.1) — 앱 세이브가 이긴다. 안 늘었으면 우편으로
젤리를 보내 유저가 직접 확장하게 한다.

## 주의

- `starter_pack` 은 이미 산 계정에 못 넣는다(`already_owned`). 스타터는
  **계정당 1회**가 상품 정의라, 여기서 뚫으면 결제한 사람과 형평이 깨진다.
- 패스는 남은 기간에 **이어 붙는다**. 이미 20일 남은 계정에 주면 50일이 된다.

# 재화 정상화 (`/admin/currency`, 운영 패널 "유저" 탭)

지난 규칙에서 쌓여 **지금 규칙으로는 도달 불가능한** 값을 맞춘다.
실제 사례(2026-09-01):
- 젤리 5,983 (무과금) — 8/15 이전 수도꼭지가 **하루 193개**였다. 193x31일 ≈ 5,983.
- 재료 450억 — 스테이지 상한이 없던 시절 교환소. 스테이지 1708 에서 젤리 10 교환이
  **약 72억**을 냈다(지금은 1000 상한이라 최대 628만).

둘 다 **조작이 아니라 당시 규칙대로 얻은 것**이다. 그래서 "회수"가 아니라
"정상화"이고, 유저에게 **우편으로 사유를 알린다**.

## 입력은 **원하는 최종 값** 그대로

젤리·재료·골드는 서버 소유 필드가 **아니라서**(유저가 스스로 버는 값이라 서버가
소유할 수 없다), 앱에 남아 있는 옛 값이 다음 업로드에 올라온다. 서버는 **1회
증가 상한**만큼만 통과시키고 `clamped` 로 알리며, 앱은 그 값을 채택하고 멈춘다.
그래서 한 번 되올라간 뒤 고정된다:

| 항목 | 1회 상한 | 착지값 |
|---|---|---|
| 젤리 | 1,000 | 입력값 + 1,000 |
| 키틴·미네랄·수액 | 20,000,000 | 입력값 + 2,000만 |
| 골드 | 200,000 | 입력값 + 20만 |

**예) 젤리를 1,500 으로 만들려면 `1500` 을 그대로 넣는다** — 서버가 상한(1,000)을
빼서 500 으로 저장하고, 앱이 되올린 뒤 1,500 에서 멈춘다. 결과 화면이 저장값과
착지값을 함께 보여준다.

⚠️ 그래서 **최종 값이 상한보다 작을 수는 없다** — 재료에 0 을 넣어도 2,000만이 남는다.

⚠️ 운영자에게 빼기를 시키지 않는다. 2026-09-01 에 "0을 넣으라는 거냐"고 되물었고,
그건 도구가 잘못 설계됐다는 신호였다 — 계산은 도구가 한다.

## 값 정하기 — 근거

- **젤리 1,500**: 무과금 최대 수입(고인물 45/일) x 출시 후 31일 ≈ 1,395.
  "오늘까지 정상적으로 모을 수 있는 최대"다. → 입력 **1500**
- **재료 2,000만**: 실측 사례(회차1·스테이지 231)에서 정상 수입은 파밍 6.5만 +
  교환소 180만 ≈ **200만**이었다. 2,000만은 그 10배라 넉넉하고, 상한 때문에
  더 내릴 수도 없다. → 입력 **20000000**
- **골드는 건드리지 않는다**: 골드는 원래 부족한 재화이고(§2.6), 문제가 된 계정도
  180K 뿐이라 진행이 골드에서 막혀 있다.

## ⚠️ 결제자는 건드리지 않는다

패널이 결제 이력을 띄운다. **산 젤리를 깎으면 환불 사유**다 — 결제 이력이 있으면
젤리 칸은 비워 둔다.
